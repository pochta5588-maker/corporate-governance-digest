# Работа с репозиторием corporate-governance-digest

## Назначение

Скилл-путеводитель по репозиторию. Описывает, что где лежит, как запускается сборка .docx, какие правила нужно соблюдать при изменениях и как публикуется результат. Используй его как источник истины, не гадая по файлам.

## Структура репозитория

```
.
├── .claude/
│   └── skills/
│       ├── q-news/
│       │   └── digest-corporate-governance.md   # Скилл сбора новостного дайджеста
│       └── repo-workflow/
│           └── SKILL.md                          # Этот скилл
├── 3 квартал-новости/                            # Готовые .docx за периоды
│   ├── Дайджест_корпоративное_управление_Q3_2026.docx      # Простой стиль
│   └── Дайджест_корпоративное_управление_Q3_2026_v2.docx   # Акцентный стиль
├── build_docx.py        # Сборка .docx: нейтральное оформление
├── build_docx_styled.py # Сборка .docx: акцентное оформление
├── digest_q3_2026.md    # Исходник дайджеста Q3 2026 (v1, простой стиль)
├── digest_q3_2026_v2.md # Исходник дайджеста Q3 2026 (v2, акцентный стиль)
├── README.md            # Описание проекта для GitHub
└── .gitignore           # macOS/Python/Claude-локальные файлы
```

**Роли файлов:**

| Файл | Роль |
|---|---|
| `build_docx.py` | Сборка .docx в нейтральном стиле, читает Markdown-исходник |
| `build_docx_styled.py` | Сборка .docx в акцентном стиле: Arial в заголовках, оранжевые линии-подчёркивания и маркеры `■`, колонтитулы, синие гиперссылки |
| `digest_*.md` | Исходники дайджестов, пишутся скиллом `q-news` |
| `3 квартал-новости/` | Результат работы сервиса — готовые .docx |
| `.claude/skills/q-news/…` | Методика сбора новостей: источники, фильтры, 7 разделов, формат карточки |

**Важно — про историю репозитория:** в проекте не должно быть следов стороннего брендинга (логотип, фирменные скрипты, упоминания НОКС). Они удалены и не должны возвращаться ни в новые файлы, ни в README, ни в .docx, ни в историю — см. раздел «Ограничения и запреты» ниже.

## Основной сценарий: сборка (обновление) .docx

Это и есть «запуск сервиса». Сервис не имеет сервера: агент собирает новости (скилл `q-news`), Python-скрипты собирают .docx.

1. Проверь, установлен `python-docx` (если нет — `pip install python-docx` и сообщи об этом).
2. Собери .docx из Markdown-исходника:

   ```bash
   # нейтральное оформление
   python3 build_docx.py digest_<квартал>_<год>.md "3 квартал-новости/Дайджест_корпоративное_управление_<квартал>_<год>.docx"

   # акцентное оформление
   python3 build_docx_styled.py digest_<квартал>_<год>.md "3 квартал-новости/Дайджест_корпоративное_управление_<квартал>_<год>_v2.docx"
   ```

3. Проверь, что файл создан, размер разумно вырос относительно исходника (десятки КБ), и сообщи полный путь.
4. Если пользователь просит «пересобери» после правки .md — повтори ту же команду. Скрипты перезаписывают .docx без вопросов.

Markdown — подмножество, поддерживаемое скриптами (не полный Markdown):

- заголовки `#`, `##`, `###`;
- маркированные списки `- `;
- строки, начинающиеся на `Период:` (титул + линия-подчёркивание) и `Примечание:` (служебное примечание);
- жирный `**текст**`, ссылки `[текст](url)`;
- всё остальное (таблицы, картинки, `###` уровня 1, HTML) при сборке станет обычным абзацем.

## Внесение изменений

**В дайджесты (`digest_*.md`):**

- сохраняй структуру из 7 разделов: Новости законодательства → Законодательные инициативы → Новости Банка России → Новости рынка ценных бумаг → Раскрытие информации → Правоприменительная практика → Исследования (полные правила — скилл `q-news`);
- в каждой новости: `### Заголовок`, строка `ДД.ММ.ГГГГ · Источник: [Название](url)`, абзац 3–5 предложений;
- новости внутри раздела — в хронологическом порядке;
- правь только тот исходник, о котором говорит пользователь (v1 и v2 — независимые версии: v1/простой стиль, v2/акцентный).

**В скрипты (`build_docx*.py`):**

- формат вывода — Word .docx через `python-docx`; менять целевой формат (HTML, PDF, Google Docs) можно только по явной просьбе пользователя и только новым скриптом, не трогая существующие;
- при правке сначала скомпилируй: `python3 -m py_compile build_docx.py build_docx_styled.py`;
- затем пересобери оба имеющихся .docx (см. «Основной сценарий») и убедись, что сборка прошла без ошибок и файл создаётся заново.

**В README.md:**

- README описывает проект по разделам: проблема → пользователь → основная функция → формат результата → MVP → технологии → как пользоваться → структура репозитория; сохраняй этот порядок;
- при добавлении/переименовании файлов синхронизируй дерево «Структура репозитория» с реальными файлами (`ls -R`, дерево в README должно совпадать по названиям);
- если меняются команды запуска, имена скриптов или аргументы — обнови раздел «Как пользоваться» и скомпилируй дерево в README заново;
- не добавляй в README упоминаний сторонних брендов, логотипов и брендбуков.

## Проверка ошибок

Перед публикацией и после любых правок:

1. Скрипты компилируются: `python3 -m py_compile build_docx.py build_docx_styled.py` (молча = ок).
2. Сборка обоих скриптов на имеющихся исходниках успешна, файлы создаются.
3. Собранный .docx не содержит упоминаний стороннего брендинга:

   ```bash
   for f in "3 квартал-новости"/*.docx; do unzip -p "$f" "word/*.xml" 2>/dev/null | grep -c "НОКС"; done
   # должно быть 0
   ```
4. Git: `git status --short` — не должно быть неожиданных файлов; `.DS_Store`, `__pycache__/`, `*.pyc`, `.claude/settings.local.json` игнорируются (.gitignore); не коммитить их руками.
5. Нет локальных изменений, которые пользователь не упоминал в запросе.

## Публикация (коммит и пуш)

Репозиторий публичный: https://github.com/pochta5588-maker/corporate-governance-digest, ветка `main`, пуш через `gh`/https.

1. Проверь статус: `git status --short`, `git diff`.
2. Компактное сообщение коммита: что и зачем изменено (1 строка), затем строка атрибуции:
   ```
   Co-Authored-By: Claude Code <noreply@anthropic.com>
   ```
3. Публикуй: `git push origin main`.
4. Подтверди результат и дай пользователю ссылку на репозиторий; при необходимости — `gh api "repos/<owner>/<repo>/git/trees/main?recursive=1" --jq '.tree[].path'`, чтобы убедиться, что дерево файла на GitHub соответствует локальному.

**Запрещено:**

- перезапись истории (`--force`, amend опубликованных коммитов) — репозиторий один раз уже был пересоздан из-за истории с брендингом; не повторяй этого без прямой просьбы пользователя;
- пуш секретов, ключей, токенов;
- публикация файлов, не вошедших в репозиторий ранее (логотипов, брендбуков, служебных файлов).

## Ограничения и запреты (обязательно к соблюдению)

- **Без брендинга НОКС.** В проекте не должно быть: файлов с именем `build_docx_nokc*`, PNG-логотипа, цветов/шрифтов, задокументированных как «фирменные» чужой организации, упоминаний НОКС/брендбука в коде, README, скиллах. Палитра акцентного стиля — нейтральные «оранжевый/тёмно-серый/серый/светло-серый» без ссылок на чужие брендбуки; колонтитулы — нейтральные («Дайджест по корпоративному управлению»).
- Стили дайджеста: v1 — `build_docx.py`, v2 — `build_docx_styled.py`; не перепутать при пересборке.
- Число коммитов: не создавать коммиты автоматически — только по прямой просьбе пользователя.
- Ссылки в дайджестах — на официальные источники (cbr.ru, consultant.ru, garant.ru, interfax.ru и др. по списку скилла `q-news`); не проверенные ссылки не включать.

## Типовые запросы

- **«Покажи, что в проекте»** — выведи дерево файлов и укажи, за что каждый файл отвечает.
- **«Пересобери дайджест»** — найди нужный `digest_*.md`, запусти соответствующий скрипт, проверь .docx на брендинг, назови путь до результата.
- **«Исправь ошибку в сборке»** — `py_compile`, построй минимальный тест .md, отследи в какой секции скрипта проблема (для стилизаторов: `set_font`, `add_runs_with_links`, `para`, `set_bottom_border`).
- **«Обнови README»** — синхронизируй с реальной структурой и разделами README.
- **«Подготовь проект к публикации»** — прогони все проверки из пункта «Проверка ошибок», составь короткий отчёт о готовности (что изменилось, файлы, статус git), после явного подтверждения сделай коммит+пуш.
